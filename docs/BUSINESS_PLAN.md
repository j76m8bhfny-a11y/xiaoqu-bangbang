## 一、执行摘要

**左邻右帮**是一款面向城市住宅小区的社区互助微信小程序，已完成了从需求验证到产品锁版的全流程（PRD v0.8.0，23 个功能模块，M1-M23 全部实现）。产品以"邻里互助"为核心，通过小红花激励体系重建社区信任关系。

本计划书提出在现有产品基础上引入 **AI Agent 能力层**，将左邻右帮从"信息撮合平台"升级为"智能社区协作平台"。通过 6 大 AI Agent 模块，实现供需智能匹配、社区治理自动化、内容深度审核、运营数据洞察等能力升级，同时构建"基础免费 + AI 增值 + 社区 SaaS + 本地生活"的复合商业模式。

**核心数据假设**（Year 1 目标）：

| 指标               | 目标         |
| ------------------ | ------------ |
| 覆盖小区           | 500+         |
| 认证用户           | 10 万+       |
| 月活用户           | 5 万+        |
| 月均互助事件       | 2 万+        |
| AI Agent 调用量/月 | 50 万+       |
| 预计年收入         | 300-500 万元 |

## 二、市场分析

### 2.1 市场背景

**宏观趋势**：

- 中国城镇化率超 65%，城市小区超 50 万个，覆盖人口 8 亿+
- "陌生人社区"问题突出：超 70% 城市居民不认识邻居，社区归属感持续下降
- 物业管理矛盾频发：业主-物业-业委会三方信息不对称，缺乏透明议事渠道
- 国家政策推动："完整社区"试点、基层治理数字化、"15 分钟生活圈"

**AI 行业趋势**：

- LLM 成本快速下降（GPT-4o/Claude/国产大模型 API 成本已降至可商用水平）
- Agent 框架成熟（LangChain/AutoGen/CrewAI 等降低开发门槛）
- 微信小程序 + AI 成为新流量入口（小程序 DAU 6 亿+，AI 小程序增速 300%+）
- 国家《生成式人工智能服务管理暂行办法》为合规 AI 应用提供框架

### 5.2 六大 AI Agent 模块

#### Agent 1：供需匹配 Agent

**目标**：将"人找事/事找人"从被动浏览升级为主动推荐。

**能力**：

- 用户发布求助事件时，Agent 分析事件内容 + 用户技能档案 + 历史互助记录 + 时间偏好，主动推送 N 个最优匹配帮手
- 帮手收到推送后可一键响应，降低发现成本
- 闲置物品发布时，Agent 基于小区历史交易数据 + 市场行情智能估价，给出定价建议
- 购物拼拼发布时，Agent 自动匹配同小区有相似需求的用户，推荐合并拼单

**技术方案**：

- LLM 提取事件关键信息（类型/技能/位置/时间）
- 向量检索（pgvector）匹配技能档案 + 历史事件
- 规则引擎叠加：认证状态、活跃度、历史好评率
- 推送通道：小程序订阅消息 + 站内通知

**指标**：

- 匹配响应率 > 60%（当前被动浏览约 20%）
- 平均匹配时间 < 30 秒
- 用户满意度 > 4.0/5

#### Agent 2：社区管家 Agent

**目标**：7×24 社区问答助手，覆盖物业咨询、生活服务、规则查询。

**能力**：

- 自然语言问答："怎么发起议题？""我的认证什么时候通过？""附近有什么便民服务？"
- 知识库：小区公告 + 议题决议 + 物业规定 + 平台使用指南 + 图文教程
- 智能引导：根据用户意图自动跳转对应功能页（"我想发个闲置" -> 跳转闲置发布页）
- 物业对接：非平台范围问题自动生成工单转物业（预留接口）

**技术方案**：

- RAG（检索增强生成）：小区知识库 + 平台 FAQ
- Function Calling：调用现有 API（查通知/查认证状态/查排名等）
- 上下文记忆：多轮对话保持上下文
- 多小区隔离：按 communityId 隔离知识库

**指标**：

- 问题首次解决率 > 70%
- 平均响应时间 < 3 秒
- 日均对话轮次 > 5,000

#### Agent 3：内容审核 Agent（升级现有 Mock）

**目标**：从关键词匹配升级为 LLM 深度审核，提升审核准确率和安全性。

**能力**：

- 文本审核：色情/暴力/赌博/诈骗 + 隐性违规（暗语/谐音/emoji 替代）+ 广告引流 + 个人信息泄露
- 图片审核：接入视觉模型，识别违规图片 + 图片文字 OCR 二次审核
- 上下文审核：结合用户历史行为判断是否恶意发布
- 审核理由生成：reject 时给出可理解的拒绝原因（而非"包含违规内容"）
- 申诉处理：用户申诉时 Agent 重新审核，辅助人工决策

**技术方案**：

- LLM 审核 prompt + 分类标签
- 图片审核：视觉 API（阿里云/腾讯云内容安全）
- 审核日志：保留完整审核链路（输入 -> prompt -> 输出 -> 决策）
- 人工审核队列：manual_review 状态自动入队

**指标**：

- 审核准确率 > 95%（当前关键词匹配约 70%）
- 误判率 < 2%
- 审核延迟 < 2 秒

#### Agent 4：议事分析 Agent

**目标**：将议题讨论从"信息堆积"升级为"结构化洞察"。

**能力**：

- 议题智能摘要：长讨论自动提取核心观点、正方/反方论据、共识点、分歧点
- 情感分析：监控讨论情绪走向，冲突升级时预警管理员
- 议题聚类：相似议题自动归组，推荐合并（升级现有 Jaccard 匹配）
- 投票建议：基于讨论趋势生成投票选项建议
- 议题报告：议题完结时自动生成结构化报告（背景/讨论过程/结论/执行建议）

**技术方案**：

- LLM 摘要 + 观点抽取
- 情感分析模型（可用 LLM zero-shot）
- 向量聚类（HDBSCAN + embeddings）
- 报告模板：LLM 填充结构化模板

**指标**：

- 摘要准确率 > 85%
- 冲突预警召回率 > 80%
- 议题报告生成率 100%（完结议题）

#### Agent 5：运营助手 Agent

**目标**：为 Admin 后台注入 AI 能力，降低运营人力成本。

**能力**：

- 智能仪表盘：自然语言查询运营数据（"本月哪个小区最活跃？""上周举报处理时效如何？"）
- 异常检测：自动发现数据异常（某小区突然大量发布、某用户刷积分等）
- 自动报告：周报/月报自动生成，包含关键指标、趋势分析、建议
- 内容推荐：管理员审核队列智能排序（高风险内容优先）
- 用户画像：基于互助/闲置/议事行为生成社区用户画像

**技术方案**：

- Text-to-SQL：自然语言查询数据库
- 时序异常检测：统计模型（Z-score / IQR）
- 报告模板：LLM 填充
- 推荐排序：风险评分模型

**指标**：

- 运营效率提升 50%（审核/报告/数据查询）
- 异常检测召回率 > 75%
- 周报自动生成率 100%

#### Agent 6：安全守护 Agent

**目标**：主动安全防护，从被动举报升级为主动发现。

**能力**：

- 行为异常检测：刷积分/批量发布/恶意举报/骚扰行为
- 内容关联分析：跨事件/跨用户关联分析，发现团伙行为
- 纠纷预警：互助过程中的沟通异常（如频繁取消/差评）自动预警
- 自动处理：低风险自动处理（如限制发布频率），高风险转人工
- 安全报告：月度社区安全报告

**技术方案**：

- 规则引擎 + ML 异常检测
- 用户行为时序分析
- 知识图谱关联分析（跨事件/跨用户）

**指标**：

- 异常行为检测召回率 > 80%
- 误报率 < 5%
- 月度安全报告生成率 100%

| 组件       | 选型                                | 理由                            |
| ---------- | ----------------------------------- | ------------------------------- |
| LLM        | 国产大模型（通义千问/DeepSeek/GLM） | 成本低、合规、中文能力强        |
| 向量数据库 | pgvector（PostgreSQL 扩展）         | 复用现有 PG，无额外运维         |
| Embedding  | BGE-M3 / text-embedding-3-small     | 中文效果好 / 成本低             |
| Agent 框架 | 自研轻量框架                        | 场景明确，不需要通用 Agent 框架 |
| RAG        | LangChain + pgvector                | 成熟生态                        |
| 消息队列   | Redis Streams（已有 Redis 依赖）    | 轻量异步任务                    |
| 内容安全   | 阿里云/腾讯云内容安全 API           | 合规要求                        |

### 7.2 LLM 网关设计

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Agent 调用   │────▶│  LLM 网关    │────▶│  模型路由     │
│  (6 个 Agent) │     │  (统一入口)   │     │  - 通义千问   │
└──────────────┘     │  - 限流       │     │  - DeepSeek  │
                     │  - 计费       │     │  - GLM       │
                     │  - 降级       │     │  - 本地模型   │
                     │  - 日志       │     └──────────────┘
                     └──────────────┘
```

**关键设计**：

- 统一网关：所有 Agent 调用 LLM 通过网关，统一限流/计费/降级
- 模型路由：简单任务用小模型（成本低），复杂任务用大模型（质量高）
- 降级策略：LLM 超时/失败时降级为规则引擎
- 成本控制：单用户单日 AI 调用上限 + 缓存

### 7.3 数据流

```
用户操作 ──▶ 事件触发 ──▶ Agent 任务队列 ──▶ Agent 执行 ──▶ 结果回写
                              │
                    ┌─────────┼─────────┐
                    ▼         ▼         ▼
              LLM 调用    向量检索    规则引擎
              (异步)      (同步)      (同步)
```

### 7.4 与现有架构集成

| 现有组件   | AI 集成方式                                      |
| ---------- | ------------------------------------------------ |
| NestJS API | 新增 `modules/ai/` 模块，Agent 作为 Service 注入 |
| PostgreSQL | 加 pgvector 扩展，新增 `ai_embeddings` 表        |
| Prisma     | 新增 Agent 相关模型（Task/Log/Config）           |
| Redis      | Agent 任务队列 + LLM 响应缓存                    |
| Admin 后台 | 新增 AI 监控面板（调用量/成本/效果）             |
| 小程序     | 新增 AI 助手入口（Tab/悬浮按钮）                 |

## 八、运营策略

### 8.1 用户增长

**冷启动阶段（0-500 小区）**：

- 种子小区：选择 10 个配合度高的试点小区，人工运营 + 产品共创
- 小区申请裂变：现有"申请-助力"机制，申请人+助力人双激励
- 物业合作：与中小物业公司合作，免费提供 SaaS 工具换取小区入驻
- 社区活动：联合业委会举办线下活动（社区跳蚤市场、互助日），线上引导注册

**增长阶段（500-2,000 小区）**：

- 口碑传播：小红花激励体系驱动用户自发推荐
- 微信生态：分享卡片优化 + 公众号矩阵 + 视频号内容
- 城市运营：城市经理地推，与街道办/社区服务中心合作
- AI 功能差异化：供需匹配 Pro 免费体验，培养使用习惯
