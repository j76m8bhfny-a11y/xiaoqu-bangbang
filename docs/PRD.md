## 一、产品概述

### 1.1 产品定位

**左邻右帮**是一个面向城市住宅小区的**公益型社区互助微信小程序**，让同小区邻居之间基于"小事"互相帮忙——借工具、帮忙取快递、遛狗时顺带看护、转让闲置物品、讨论小区公共事务——通过小红花和排行榜激励持续互助，重建邻里关系。

### 1.2 核心价值

| 对用户                             | 对小区                             | 对平台                             |
| ---------------------------------- | ---------------------------------- | ---------------------------------- |
| 身边小事有人帮，不用总麻烦亲友     | 邻里关系从"陌生"到"熟悉"           | 积累社区互助数据，验证邻里互助模式 |
| 闲置物品流转到需要的邻居手里       | 公共事务有讨论渠道，不再只靠物业群 | 通过小区申请机制自然扩展覆盖范围   |
| 帮人有成就感（小红花/排行榜/勋章） | 业委会议事有据可依                 | ---                                |

### 1.3 目标用户

- **城市商品房小区业主/租客**，年龄 25-55 岁，有智能手机，微信活跃用户
- 特别关注**老年用户友好**：大字号、高对比度、简洁操作路径（设计系统"草木绿 v2 老年友好版"）

### 1.4 非目标（本期不做）

- **不做支付**：闲置交易仅线上联系，不接入微信支付
- **不做真实 AI/OCR**：内容审核和证件识别保持 Mock 实现，不接入真实服务商
- **不做跨小区社交**：所有业务数据按小区隔离，不跨小区推荐/展示
- **不做即时通讯**：不提供私聊功能，通过联系方式自行沟通
- **不做 CI/CD**：本期无自动化部署流水线

## 二、用户角色

### 2.1 角色体系

| 角色         | 标识                      | 权限                                         | 获取方式           |
| ------------ | ------------------------- | -------------------------------------------- | ------------------ |
| 普通居民     | `resident` + `unverified` | 已选小区，可浏览内容，**不可发布、不可投票** | 选择小区后自动创建 |
| 认证业主     | `resident` + `verified`   | 可发布事件/闲置/评论/议题、投票、认领身份    | 提交认证材料通过   |
| 业委会管理员 | `committee_admin`         | 认证业主权限 + 管理本小区公告/投票/业委会    | 平台管理员分配     |
| 平台管理员   | `platform_admin`          | 全部管理权限（所有小区）                     | 平台运营人员       |

### 2.2 角色流转

```
微信登录 → 普通居民 → 提交认证材料 → 认证业主
                                ↓
                        (平台分配) → 业委会管理员
                                  ↓
                          (平台运营) → 平台管理员
```

### 2.3 关键权限矩阵

| 操作           | 普通居民 | 认证业主 | 业委会管理员 | 平台管理员 |
| -------------- | -------- | -------- | ------------ | ---------- |
| 浏览内容列表   | ✓        | ✓        | ✓            | ✓          |
| 发布事件/闲置  | ✗        | ✓        | ✓            | ✓          |
| 评论/点赞      | ✗        | ✓        | ✓            | ✓          |
| 发起议题       | ✗        | ✓        | ✓            | ✓          |

| 业主认证       | ✓        | —        | —            | —          |
| 管理本小区内容 | ✗        | ✗        | ✓            | ✓          |
| 管理所有小区   | ✗        | ✗        | ✗            | ✓          |

## 三、典型用户场景

### 场景 1：新用户从注册到首次互助

```
1. 微信扫码/搜索进入小程序 → 登录页（必须登录，无游客模式）
2. 微信一键登录 → 选择小区（搜索小区名）
3. 进入首页（小区事 tab）→ 看到公告/投票/议题
4. 切到"邻里帮"tab → 看到求助列表
5. 点击"我来帮"→ 响应求助 → 联系发布者
6. 完成互助 → 帮手申请完成 → 创建者确认 → 帮手获得小红花
```

### 场景 2：发布求助→响应→完成→评价

```
1. 认证业主点击"+"→ 选择"求助"
2. 填写标题/描述/图片 → 选择奖励方式（免费/协商/有偿）
3. 提交 → AI 审核文本+图片 → 通过 → 事件发布
4. 邻居看到 → 点击"我来帮"→ 发布者收到通知（同一用户不可重复响应）
5. 发布者选择帮手 → 帮手收到通知
6. 互助完成 → 帮手申请完成 → 发布者确认完成
7. 帮手获得小红花 → 积分/勋章/排行更新（求助类创建者不发花，只记贡献）
```

### 场景 3：闲置流转

```
1. 认证业主点击"+"→ 选择"发闲置"
2. 选分类/填标题/上传图片/选成色/选交易方式
3. AI 审核文本+图片 → 通过 → 上架
4. 邻居看到 → 点击"我想要"→ 显示联系方式（✅ 意向记录系统已实现, batch 5, commit 62f3ec4, 详见 §8.1）
5. 交易完成 → 卖家标记"已售"（买家选择+互评后续迭代）
```

### 场景 4：议事参与

```
1. 认证业主在"小区事"tab 看到议题
2. 点击议题 → 查看详情 → 点赞/点踩（open/closed 两个作用域，随时可表态）
3. 查看相关事件时间线 → 发表讨论
4. 发布公共反馈事件时选择/创建议题（新建议题需 AI 审核通过）
5. 议题完结后 → 评分
6. 发起议题通过审核 → 获得 1 朵小红花 + 议事发起人奖章
```

### 场景 5：小区申请闭环

```
1. 用户搜索不到自己小区 → "申请开通"
2. 填写小区信息 + 上传证明材料 → 提交
3. 转发给邻居 → 邻居助力（增加通过概率）
4. 平台管理员审核 → 通过 → 自动创建小区
5. 申请人获得"创始人"徽章 → 自动认证为业主 → 进入小区
```

## 四、功能模块详解

> 每个模块按**功能描述 → 关键流程 → 业务规则 → 页面结构**描述。
> API 端点/DTO/表结构详见 Map.md 和 Spec.md。

---

### 4.1 认证与身份 (M1)

**功能描述**：微信一键登录、个人资料管理、用户公开主页。

**关键流程**：

- 登录：微信 code → 后端换 openid → 签发 JWT → 前端缓存 token
- 首次登录：无小区 → 跳转选择小区页
- 再次登录：有 token → GET /me 恢复用户状态 → 有小区则进首页

**业务规则**：

- JWT 有效期 7 天
- 用户主页不返回 openid/status，徽章最多展示 6 个
- 手机号/微信号/楼栋房号：用户可自选展示方式（✅ 技能匹配已实现 §4.19, batch 7, commit 3c4f5b5, 联系方式字段已就绪）
- 跨小区查看用户主页时 verifyStatus 显示 null（不显示"未认证"标签）

**页面**：login（登录）/ home（我的）/ profile-edit（编辑资料）/ user-profile（他人主页）

---

### 4.2 小区选择与数据隔离 (M2)

**功能描述**：搜索并选择小区、小区数据隔离。

**关键流程**：

- 搜索小区名/城市 → 选择 → 后端创建 community_member 记录（role=resident, verifyStatus=unverified）
- 所有后续业务请求自动携带 currentCommunityId

**业务规则**：

- 首次选择自动创建 community_member，重复选择不重复创建
- 未选小区请求业务接口返回 40301"请先选择小区"
- 所有业务数据（事件/闲置/议题/投票/公告/排行榜/通知）按 communityId 过滤
- 社群入口按认证状态过滤：未认证仅见 public，认证可见 verified_only
  > 注：社群入口小程序端本期不做（页面已注释），仅后端 API 和 Admin 后台可用

**页面**：community-select（搜索选择）

---

### 4.3 业主认证 (M3)

**功能描述**：业主身份认证，上传材料→OCR识别→AI匹配→审核结果。

**关键流程**：

1. 选择材料类型（房产证/租房合同/门禁卡/其他）
2. 上传材料照片
3. 同意授权（consentAccepted）
4. 提交 → OCR 识别材料信息 → AI 匹配小区名+地址
5. 置信度 ≥ 0.8 且名字匹配 → 自动通过
6. 置信度 < 0.8 → 转人工审核
7. 通过 → 更新 verifyStatus=verified → 前 30 名发"首批业主"徽章 → 原图标记删除

**业务规则**：

- 必须同意授权才能提交
- 前 30 名认证业主获得 `first_owner_top30` 徽章（幂等发放）
- 认证通过后原始文件标记待删除（不留存敏感证件）
- 未认证用户（verifyStatus≠verified）不可发布内容（返回 40302）

**页面**：verify（认证提交 + 认证记录）

### 4.4 邻里互助事件 (M4)

**功能描述**：邻里互助事件全生命周期管理。事件按类型分为**互助类**和**议事类**两大类，各自走不同生命周期。

> **help_offer（我能帮忙）已从事件类型移除**，改为个人技能档案 + 匹配机制（详见 §4.19）。用户在个人资料维护"我能帮忙"清单，有人发求助时系统自动匹配。

**事件类型**（6 种，分互助类和议事类）：

| 类型                       | 分类 | 场景                                              | CTA 文案 | CTA 行为   |
| -------------------------- | ---- | ------------------------------------------------- | -------- | ---------- |
| 求助 (help_request)        | 互助 | 请求邻居帮忙（借工具/取快递/帮忙看护）            | 我来帮   | 响应求助   |
| 公益 (public_welfare)      | 互助 | 公益活动（小区清洁/爱心捐赠）                     | 我要报名 | 报名参与   |
| **宠物帮帮 (pet_help)**    | 互助 | 代喂/代遛/寻宠（子分类，详见 §4.21）              | 联系 TA  | 响应/联系  |
| **购物拼拼 (group_buy)**   | 互助 | 求代购/代购方拼单（信息同步，不结算，详见 §4.22） | 我要加入 | 加入拼单   |
| 公共反馈 (public_feedback) | 议事 | 议事类反馈，**必须挂议题**                        | 关注进展 | 跳转评论区 |
| 讨论 (discussion)          | 议事 | 议事讨论，**必须挂议题**                          | 参与讨论 | 跳转评论区 |

> **宠物帮帮（pet_help）** 和 **购物拼拼（group_buy）** 详见 §4.21 / §4.22。两者均在"邻里帮"tab 的 filter 中作为独立筛选项展示。
> **老 lost_found 类型已废弃**，老数据迁移到 `pet_help` + `subType=lost`（详见 §4.21）。
> **邻里帮 filter**：全部（含 help_request/public_welfare/pet_help/group_buy）/ 求助 / 公益 / 宠物帮帮 / 购物拼拼。"全部"调用多类型联合查询。

**事件生命周期（按类型区分）**：

互助类（help_request / public_welfare / pet_help）：

```
pending_review → open → in_progress（有人响应）→ processing（选中帮手）→ completed（双方确认）
                → rejected（审核拒绝）
                → closed（创建者关闭）
```

- public_welfare / pet_help.lost 设计支持选**多个**帮手/参与者（✅ **多帮手流程已实现** (batch 6, commit 04688e3)：EventParticipant 表 + 逐个确认发花。详见 §8.1）
- **多帮手完成确认**（设计方向）：创建者**逐个确认**每个帮手是否参与，确认一个发一个的花；未确认的帮手不得花。与单帮手的"completed 时统一触发"不同——多帮手为逐个触发，单帮手为完成时触发

议事类（public_feedback / discussion）：

```
pending_review → open → closed（创建者关闭）
                → rejected（审核拒绝）
```

> 议事类事件禁用 in_progress/processing/completed 状态。respond()/selectHelper()/confirmCompletion() 对议事类事件返回 400。CTA"关注进展"/"参与讨论"跳转评论区，不改事件状态。

**关键流程**：

1. **发布**：选类型 → 填标题/描述/图片 → 议事类选议题（AI 推荐/新建）→ AI 审核文本+图片 → 发布
2. **响应**：邻居点 CTA → 事件 → in_progress → 通知创建者（**禁止重复响应**，同一用户仅一条响应记录）
3. **选帮手**：
   - help_request：创建者从响应者中选 1 个 → processing → 通知帮手
   - public_welfare：创建者选**多个**报名者为参与者 → 逐个确认 → 确认一个发一个的花（✅ 已实现, batch 6, commit 04688e3）
   - pet_help.lost（原 lost_found，迁移）：创建者选**多个**有效线索提供者 → 逐个确认 → 确认一个发一个的花（✅ 已实现, batch 6, commit 04688e3）
4. **完成确认**：
   - 单帮手（help_request）：帮手申请完成 → 创建者确认 → completed。**R11 双方确认**：一对一劳动需帮手主动表态"做完了"，创建者确认后才算完成
   - 多帮手（public_welfare/pet_help.lost）：创建者逐个确认每个帮手是否参与 → 全部确认后 → completed。**参与确认**：多帮手场景（如社区大扫除）是确认"谁来了"，而非"做完了"，无需帮手申请。R11 的双方确认针对一对一互助，多帮手为参与确认
5. **送花感谢**：创建者可给帮手送花感谢（本期唯一反馈机制；结构化评价 rating+tags+content 为后续迭代）
6. **激励触发**：完成时自动计算小红花 → 检查勋章 → 重算排行 → 发通知

**业务规则**：

- **匿名发布**：isAnonymous=true 时，非本人看不到创建者信息（后端 maskAnonymous 脱敏）；**管理员可见匿名事件创建者**（用于审核管理，Admin 直接访问数据不经脱敏）
- 议事类事件必须挂 topicId，非议事类不能挂
- **编辑限制**：有人响应后（in_progress/processing）禁止编辑核心内容（标题/描述/图片）；closed/completed 不可编辑
- **图片审核**：编辑时图片变化也触发 AI 审核（不仅限文本变化）
- **奖励方式**（rewardType: free/paid/negotiable/none）仅适用于 help_request 类型，用于展示和筛选，不影响小红花数量（统一 1 朵）
- 结构化评价（rating+tags+content）为后续迭代，本期仅送花感谢
- **禁止重复响应**，同一用户仅一条响应记录；**创建者不可响应自己的事件**（代码定稿后补检查）
- 感谢不可重复、不可感谢自己
- help_request 完成需帮手申请+创建者确认（防单方刷积分）；多帮手为创建者参与确认
- AI 审核触发点：创建/编辑（含图片变化）/评论
- **评论嵌套最多 2 层**（第 3 层返回 400，与议题评论一致）
- **自动过期**：open/in_progress/processing 状态超过 30 天无活动，自动转 closed（不触发激励）。"活动"仅指新响应（EventApplication 创建）和状态变更，评论/点赞不重置计时器。需定时任务每日扫描（✅ 已实现, batch 4, commit 51423f4, EventsCron 每天凌晨 3 点执行）

**详情页状态→按钮映射**（✅ 已实现 CTA 状态判断, batch 2, commit 0fba0d4, 见 findings P-74）：

| 状态           | CTA(响应)      | 编辑         | 关闭         | 确认完成     | 申请完成       | 送花感谢     | 举报           |
| -------------- | -------------- | ------------ | ------------ | ------------ | -------------- | ------------ | -------------- |
| pending_review | 隐藏           | 隐藏         | 隐藏         | 隐藏         | 隐藏           | 隐藏         | 隐藏           |
| open           | 显示(非创建者) | 显示(创建者) | 显示(创建者) | —            | —              | —            | 显示(非创建者) |
| in_progress    | 显示(非创建者) | 隐藏         | 显示(创建者) | 显示(创建者) | 显示(选中帮手) | —            | 显示(非创建者) |
| processing     | 隐藏           | 隐藏         | 显示(创建者) | 显示(创建者) | 显示(选中帮手) | —            | 显示(非创建者) |
| completed      | 隐藏           | 隐藏         | 隐藏         | —            | —              | 显示(创建者) | 显示(非创建者) |
| closed         | 隐藏           | 隐藏         | 隐藏         | —            | —              | —            | 显示(非创建者) |
| rejected       | 隐藏           | 隐藏         | 隐藏         | —            | —              | —            | 隐藏           |

> "—"表示该按钮在此状态不适用（不显示）。赞/评论/收藏在 open~completed 状态可用，closed/rejected 后禁用。

**页面**：events（列表）/ event-detail（详情）/ event-create（创建）/ event-edit（编辑）

### 4.5 闲置市集 (M5)

**功能描述**：二手闲置物品发布与流转。

**分类体系**：

| 分类 | 代码      |
| ---- | --------- |
| 免费 | free      |
| 家具 | furniture |
| 母婴 | baby      |
| 书籍 | books     |
| 宠物 | pet       |
| 数码 | digital   |
| 其他 | other     |

**交易方式**：出售 (sell) / 免费 (free) / 交换 (exchange)
**成色等级**：全新 (new) / 九成新 (like_new) / 八成新 (good) / 七成新 (used) / 旧物 (old)

**生命周期**：

```
pending_review → on_sale → sold（标记已售，选择买家）
               → rejected
               → closed（下架/隐藏）
```

- **卖家下架**：卖家可自行关闭未售出商品（代码定稿后补 `POST /market/items/:id/close`，与事件 close 一致）
- **管理员隐藏**：管理员可隐藏违规商品（`POST /admin/market/:id/hide`），可恢复（`POST /admin/market/:id/restore`）

**意向记录**（"想要"）（✅ **已实现** (batch 5, commit 62f3ec4), 详见 §8.1。MarketInterest 表 + "我想要"意向记录 + markSold 选买家 + 评价）：

- 用户点击"我想要"→ 记录意向（MarketInterest）→ 联系卖家

### 4.6 议事榜 (M6)

**功能描述**：社区公共议题讨论，关联事件，支持赞踩/评分/评论。

**议题生命周期**：

```
pending_review（AI 审核）→ open（开放讨论）→ closed（管理员关闭，填写总结）
                       → rejected（审核拒绝）
                       ← closed 可被管理员重新开放（reopen），清空关闭信息和已有评分，回到 open
```

> 议题创建时走 AI 文本审核（和事件一样），审核通过才发 1 朵小红花。**仅管理员可关闭议题**，关闭时填写总结（closedSummary），通知相关参与者。**管理员可重新开放已关闭议题**（reopen），清空 closedAt/closedBy/closedSummary，**同时清空已有评分**（ratingSum/ratingCount 归零，删除 TopicRating 记录），状态回到 open。用户需在重新关闭后重新评分。

**排序规则**：

| 状态     | 排序依据                                                                 |
| -------- | ------------------------------------------------------------------------ |
| 开放议题 | 净赞数(likeCount - dislikeCount) 降序 + 时间权重（24h 内 +5, 48h 内 +2） |
| 完结议题 | 平均星级降序 + 完结时间权重                                              |

**互动方式**：

- **赞/踩**（两个作用域）：
  - **开放态度**（open 作用域）：对议题本身的态度——"这个议题值不值得讨论"
  - **结果评价**（closed 作用域）：对议题处理结果的态度——"处理得好不好"
  - 赞踩互斥，可取消。不限制议题状态，随时可对任一作用域赞踩
  - 示例：议题刚发布时点"赞"（开放态度），议题完结后对处理结果点"赞"或"踩"（结果评价）
- **评分**：仅完结议题可评分，1-5 整数，每人一次，**提交后不可修改**
- **评论**：嵌套最多 2 层（第 3 层返回 400），通知被回复者
- **评论赞踩**：toggle 行为

**AI 功能**（4 个独立开关）：

| 开关              | 功能         | 触发时机                                                |
| ----------------- | ------------ | ------------------------------------------------------- |
| ai_topic_suggest  | 议题推荐     | 创建事件时 Jaccard 相似度推荐                           |
| ai_topic_merge    | 议题合并建议 | 管理员手动触发扫描，系统自动生成相似度 ≥ 0.8 的合并建议 |
| ai_event_comment  | 事件 AI 点评 | （预留）                                                |
| ai_content_review | 内容审核     | 事件/闲置/评论/议题创建时                               |

**业务规则**：

- 空标题返回 400
- 重复评分返回 409
- 评论第 3 层返回 400
- 合并建议状态：PENDING → APPROVED/REJECTED

**页面**：plaza（小区事首页，聚合展示）/ topics（议题列表）/ topic-detail（详情）/ topic-create（发起）

### 4.7 投票 (M7)

**功能描述**：社区投票，支持单选/多选，结果可见性可控。**投票由管理员创建**（业委会管理员/平台管理员），普通用户仅参与投票。

**投票生命周期**：

```
draft（创建，用户不可见）→ published（管理员发布，用户可见可投票）→ closed（管理员关闭，不可投票，结果按 resultVisibility 展示）
```

> 投票创建后处于 draft 状态，用户不可见。管理员发布后转 published，用户可投票。管理员关闭后转 closed，不可再投票，但结果可见性按 resultVisibility 控制。投票不可 reopen。startAt/endAt 仅用于结果可见性判断（after_end），不自动发布/关闭。

**投票配置**：

| 属性             | 说明                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| voteType         | single（单选）/ multiple（多选）                                                                                                |
| maxChoices       | 多选时最多选几项                                                                                                                |
| onlyVerified     | **待清理**：始终校验认证状态，代码定稿后移除条件判断和 onlyVerifiedLocked 字段，Admin 开关移除，小程序标签始终显示              |
| resultVisibility | always（始终可见）/ after_vote（用户自己投票后可见——必须先投票才能看结果）/ after_end（投票结束后可见）/ admin_only（仅管理员） |
| isAnonymous      | 是否匿名投票                                                                                                                    |

**业务规则**：

- 一人一票（UNIQUE(voteId, userId)）
- **始终要求认证业主身份**，未认证返回 403（不论 onlyVerified 值）
- **跨小区防护**：投票时校验 communityId，不可给其他小区投票
- 多选超 maxChoices 返回 400
- 结果按 resultVisibility 控制可见性
- **匿名投票**：isAnonymous=true 时，结果不显示投票者信息，仅显示各选项票数（VoteRecord 表存储 userId 但不对外返回）

**页面**：votes（列表）/ vote-detail（详情+投票+结果）

| -------------- | ------------------------------ |

**求代购 (seek) 创建字段**：

- 商品清单（多商品，**必填至少 1 个**）
  - 商品名（必填）
  - 数量

**状态机**：

```
pending_review（审核中）-> open（接单中）
                       -> rejected（审核拒绝）
                       -> closed_for_bid（已截止接单）-> purchased（已购回）-> completed（已完成）
                                                                                       -> closed（发起人关闭）
```

> 5 个中间态：截止接单和已购回是关键节点，影响响应人行为。截止接单后不能新增响应，但可查看；已购回后进入分发阶段。

4. **截止接单**：主买人点击截止 -> closed_for_bid -> 通知所有响应人
5. **采购**：主买人线下采购 -> 标记"已购回" -> purchased -> 通知所有响应人
6. **分发**：主买人逐个标记 Item.delivered -> 全部 delivered 后 -> **自动**转 completed（无需手动调用 complete）

**通知触发**：

## 五、全局业务规则

### 5.1 小区数据隔离

- **原则**：所有业务数据按 communityId 隔离，不跨小区展示/推荐
- **实现**：CurrentCommunityGuard 强制要求已选小区，Service 层 where 条件过滤
- **例外**：platform_admin 使用 @SkipCurrentCommunity() 可跨小区操作（如小区申请审批）
- **红线**：不可绕过（详见 Map.md R2）

### 5.2 匿名机制

- **事件匿名**：
  - 触发：事件 isAnonymous=true
  - 脱敏：后端 maskAnonymous() 对非本人返回 creator=null
  - 本人：保留 creatorId（可看到自己是谁发的）
  - 分享：匿名事件分享标题不含创建者信息
- **投票匿名**：
  - 触发：投票 isAnonymous=true
  - 脱敏：结果不显示投票者信息，仅显示各选项票数
  - 存储：VoteRecord 表存储 userId（用于防重复），但不对外返回
- **红线**：不可泄露匿名发布者/投票者身份（详见 Map.md R1）

### 5.3 业主认证体系

- **流程**：上传材料 → OCR → AI 匹配 → 自动/人工审核
- **自动通过**：置信度 ≥ 0.8 且社区名匹配
- **人工审核**：置信度 < 0.8 或名字不匹配
- **权益**：认证后方可发布内容、投票、认领身份
- **激励**：前 30 名认证业主获"首批业主"徽章
- **隐私**：认证通过后原图标记删除，不留存敏感证件
- **红线**：原图必须删除（详见 Map.md R5）

### 5.4 激励体系

**五套独立激励体系**，各自独立计算：

- **互助激励**：互助类事件（help_request/public_welfare/pet_help）完成时，给帮手发花；创建者按类型决定是否发花（求助/寻宠/代喂/代遛/购物拼拼不发，公益发花）；group_buy 走独立表，完成时给主买人发 1 朵
- **议事激励**：议事类事件（public_feedback/discussion）通过审核时，给创建者发 1 朵花
- **议题激励**：议题通过 AI 审核时，给创建者发 1 朵花
- **小区创建激励**：小区申请通过时，申请人获创始人徽章，助力人获种子贡献者徽章（详见 §4.9）
- **教程激励**：图文教程通过 Admin 审核时，给作者发 1 朵花 + 勋章检查（guide_1/guide_5/guide_20）（详见 §4.20）

**通用规则**：

- **小红花**：按体系和类型发放（详见 §4.9 积分规则表）
- **贡献分**：由小红花等汇总，用于排行榜
- **勋章**：自动检查并颁发（互助/议事/议题/教程/特殊五类，详见 §4.9 勋章规则）
- **排行榜**：月榜/总榜，事件完成/审核通过时重算（无定时任务）
- **月榜过滤**：月榜必须按 occurredAt 过滤当月，不可汇总全部历史
- **幂等**：积分 UNIQUE 防重复，勋章发放幂等

### 5.5 内容审核体系

- **AI 审核（Mock）**：文本关键词匹配 + 图片默认 pass
- **审核结果**：pass → 直接发布 / reject → 拒绝 / manual_review → 转人工
- **人工审核**：管理员在后台 approve/reject/manual-visible-admin-only
- **审核范围**：事件（创建/编辑含图片）、评论（事件/闲置）、闲置（创建）、评价（闲置）、议题（创建）、教程（创建，纯人工审核不走 AI Mock）
- **审计**：所有审核操作写入 ai_review_logs + audit_logs

### 5.6 事件生命周期

**互助类事件**（help_request / public_welfare / pet_help）：

```
pending_review（AI 审核中）
    ↓ pass
open（待响应）
    ↓ 有人响应
in_progress（有响应者）
    ↓ 创建者选帮手
processing（进行中）
    ↓ 单帮手：帮手申请+创建者确认；多帮手：创建者逐个参与确认
completed（已完成，触发互助激励）
    ↓ 或
closed（创建者主动关闭，不触发激励——创建者放弃/取消的场景）
    ↓ 或
rejected（审核拒绝）
```

**议事类事件**（public_feedback / discussion）：

```
pending_review（AI 审核中）
    ↓ pass
open（已发布，触发议事激励）
    ↓ 创建者关闭
closed（已关闭）
    ↓ 或
rejected（审核拒绝）
```

> 议事类事件不走"响应→选帮手→双方确认"流程，审核通过即发激励。

**关键约束**：

- help_request 完成需帮手申请+创建者确认（防单方刷积分）；多帮手为创建者参与确认
- 议事类审核通过即完成，无需双方确认
- 本期事件反馈仅送花感谢，结构化评价为后续迭代
- 有人响应后禁止编辑核心内容；closed/completed 不可编辑
- 红线：互助双方确认不可跳过（详见 Map.md R11）

### 5.7 议事榜与事件的关联

- 议事类事件（public_feedback / discussion）**必须**挂 topicId
- 非议事类事件**不能**挂 topicId
- 议题时间线展示关联事件（含所有状态：pending_review/open/closed，事件有人响应后不从时间线消失）
- **eventCount 更新逻辑**：仅在事件创建（审核通过）/删除/移动到其他议题时 +1/-1，事件 close 不影响 eventCount
- 议题完结后可评分（1-5 星）
- 议题创建走 AI 审核（详见 §4.6）
- AI 议题推荐：创建事件时 Jaccard 相似度匹配
